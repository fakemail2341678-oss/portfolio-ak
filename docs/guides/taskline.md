# Taskline

Taskline is the project management app at `/app/taskline` (Part 5 of [PLAN.md](../PLAN.md), section 11): one team that the admin runs from `/admin`, and a private sandbox per user so visitors can try it. It grew from Kanban (0188), which it replaced in Task 48 (0210).

**Status:** complete (Tasks 46–58). Each module has a section here, with its decision; the review and the measurements of the whole are 0226 and 0227.

## The shell (0208)

Taskline is a product of its own inside the app: nothing of the site's, the apps' or the admin's chrome.

- **Two frames.** Visitors see the public frame (`TasklinePublicFrame`: the wordmark, language, theme, sign in and sign up) on the landing, and `TasklineAuthFrame` on `/sign-in` and `/sign-up`. Everyone signed in, guests included, gets `TasklineShell` under `_shell`: the sidebar (wordmark, the workspace switcher when they have both the team and a sandbox, Home, Projects, Search, starred and recent projects, the user), the topbar (breadcrumbs, search, language, theme; the user on phones, where the sidebar is a sheet), the palette (Ctrl/⌘ K: every project, the pages, a new project where allowed, preferences), the shortcuts (`?`), the guest banner, `ConfirmProvider` and `DbScope`.
- **The brand** is `TASKLINE_BRAND` on `_taskline`'s `staticData` (`src/lib/section-brand.ts`): the root puts `emerald` on `<html data-accent>` (so portalled menus and dialogs match) and links `public/taskline/`'s icons and the Taskline manifest. Titles are `tasklineTitle(page)` ("Page · Taskline"); the landing uses `seo({ siteName: TASKLINE_NAME })`. The name is a constant, the same in every language.
- **Links** go through `links.ts` (`tasklineLinks`, `TASKLINE_PATHS`): renaming the app is a move of `src/routes/_taskline/app/taskline` and that file.
- **Who goes where:** a signed-in visitor to the landing goes to Home; a visitor to any shell page goes to Taskline's sign-in with `?redirect=`, and back afterwards. Sign-up sends the verification link to `/verify-email?redirect=…`, whose "Continue" returns to Taskline. A guest's "account" is sign-up; signing out lands on the landing.
- **404s and errors stay in the frame:** the layouts' `notFoundComponent`s render their frame (they replace the layout), and `SectionHome` makes the error and 404 pages' home link go to Taskline. An unknown or hidden workspace or project is a 404 from `loadDetailOr404`.
- **Pages:** Home (the caller's open tasks in every workspace, soonest due first; recent projects; "Start a sandbox" for an account without one, and for an account with no workspace at all, "Ask an admin to add you"); the project directory (`?view=list`, `?archived=1`, stars, `?create=1` opens "New project" for those allowed, with a key suggested from the name); a first project overview (description, progress by status, members); the account page's sections.
- **Data:** the shell's `getTasklineNav` (the workspaces with `canCreateProject`, every visible active project, the starred ones, the recent ones) and Home's `listMyTasklineTasks` resolve each of the caller's workspaces and keep what they may see. "Recent" is where the caller last recorded activity, topped up with recently changed projects. Query keys carry the user's id (`tasklineKeys`), and every write refreshes everything under it.

## The project's views (0211)

A project page is a layout (`$ws/p/$key/route.tsx`): the header (name, key, visibility, archived or read-only, the people, "Join" for a team member who may join) and the view tabs (Overview, Board, List, and Settings for those who may run it) around the view. It owns the page's `<main>`, loads the project's tasks, statuses, labels and members once (`listTasklineTasks`) for every view, and its breadcrumb is the key from the URL, which the overview renames to the project's name.

- **Overview:** the description, progress by status category and per status, the people, and the project's feed (`listTasklineProjectActivity`: the latest 30 entries with the task each is about, as sentences from `task/activity.tsx`).
- **The filters** (`projects/task-filters.tsx`; the URL params `taskFilterParams` in `search.ts`): text or reference, status, assignee (`me`, `none` or a member), label, priority, type, due (overdue, this week, none). One `<FilterBar>`, so they work without JavaScript, with a chip per filter. The board applies them to the tasks it has (`filters.ts`); the list sends them to the server, whose SQL (`listWhere`) means the same.
- **Board** (Kanban's, 0188): a column per status over a TanStack DB collection of the layout's query (`board/collections.ts`); moves and quick adds show at once and are put back if the save fails. A column over its WIP limit says so (shown, not enforced). Closed tasks leave after the done-column window (the project's `doneColumnDays`, else the workspace's 14), with a count of those hidden. `?swimlanes=assignee|priority` adds a row per assignee (unassigned last) or priority (urgent first); a task moves within its lane, and one added in a lane gets the lane's assignee or priority. A card shows the ref, type, priority, assignee, labels, the due date (overdue in the danger colour, and said), and subtask and checklist progress. Readers get no handles.
- **List:** a `DataTable` on the list contract (`taskList` in `search.ts`: sort, page and page size in the URL; `listTasklineTaskPage` pages it), board order by default. `?group=status|assignee` makes the server sort by the group first, and `DataTable`'s `groupOf` draws a heading row per group (each its own `<tbody>`). Editors get inline status, assignee and priority and bulk changes (`bulkUpdateTasklineTasks`: one change to up to 100 tasks, an entry each, one rev); everyone gets CSV export and saved views.
- **The task** (`task/task-panel.tsx`): the fields (status, assignee, priority, type, labels, dates: each change saves at once, last write wins), the title and description (TipTap, loaded lazily, saved against the version they started from: a stale save offers "Reload"), subtasks (quick add, progress), the checklist and the history. From the board and the list it opens as a sheet (`?task=WEB-12`, a masked route): the address bar, a reload, a new tab and no JavaScript give its page, `/$ws/t/WEB-12`.
- **"New task"** in the sidebar: a title in one of the caller's projects (the current one first), then the task's page.

## Finding things (0215)

- **Calendar** (`$ws/p/$key/calendar`, a view tab): a month (`?mode=month`) or a week (`week`) of the project's tasks by due date (`?by=due`) or start date (`start`), from `?date=` (omitted: today), with the project's filters. It reads the board's collection, so a reschedule shows at once and is put back if refused (saved with `patchTask`). Weeks start on the workspace's week start; its days off are shaded; days outside the month are dimmed. Open tasks without the date are in "No date" beside it. A task's handle moves it: drag it to a day (or to "No date" to clear it), dnd-kit's keyboard drag, or **Alt + ← →** (a day) and **Alt + ↑ ↓** (a week) at once; an undated task is scheduled on the day shown. Each move is announced and the focus follows the task. Readers get no handles. The grid (`calendar/grid.ts`) is pure: weeks, months, steps and My work's groups.
- **My work** (Home): open tasks assigned to the caller or watched by them in every workspace (`?show=assigned`, `watching`: watched and assigned to someone else, `all`), grouped overdue, today, the rest of this week, later and no date (`MyTasks.today` and `weekEnd`, by the first workspace's calendar).
- **Saved views** (the "Views" menu on the list, the board and the calendar): a view's search string (without `page` and `task`), the member's own or shared with the project. Anyone with a member row who may see the project saves; an editor may tick "Share"; saving a name again replaces it; 50 per member and project. The author deletes theirs, the lead a shared one. An admin reading through `taskline:read` sees the shared ones and can't save. No activity, no `rev`: views aren't project data. `useSavedViews` turns them into the `SavedViewsStore` that `DataTable`'s `savedViews` and `SavedViewsMenu` take.
- **Search** (`$ws/search?q=`, the sidebar's Search and the palette): every word must start a word of a task's title or description (a prefix tsquery over the `search` tsvector; title matches rank first), open tasks before closed ones, never the trash, in the projects the caller may see, archived included. An exact reference (`WEB-12`, any case) of a task they may see goes straight to it. The page's form submits on Enter only. The palette searches every workspace of the caller's as they type (two characters at least) and offers "Search every task for …".
- **CSV import** (the list's "Import CSV", editors): a file or pasted text (`CsvSourcePicker`, shared with Kharcha), the columns guessed from the header (title required; description, status, assignee, priority as 0–4 or its name, type, labels split on `,` `;` `|`, start, due, in the date format chosen), a preview checked by the server's schema that names what matches nothing, then one import of the valid rows, once per idempotency key. Up to 1,000 rows, 10 imports an hour, within the task quota. Names are matched without case (unmatched: the first open status, nobody, no label); each task gets `task.created` (`imported: true`), its creator and assignee watch it, and nobody is notified.
- **Sandbox:** Asha's shared list view "Due this week"; the claim moves the guest's views (their member becomes the account's) and import keys.

## Sprints and backlog (0216)

- **Turning it on:** the lead's General settings: "Use sprints" (the Backlog tab, a task's Sprint and Points, the Sprint filter) and "Estimate in" points or time. With time, the totals, charts and velocity count estimated hours (Task 53: `estimate_minutes`, typed in the backlog's rows and the task), and the report offers hours or tasks. Turning sprints off hides them; nothing is deleted, and the server doesn't refuse sprint operations either way.
- **The backlog** (`$ws/p/$key/backlog`, a view tab): the active sprint, the planned ones, then the backlog (open tasks in no sprint), each in rank order with its points total (and how many have none). A sprint planned past the recent velocity says so. Moves are the board's: drag a task's handle, dnd-kit's keyboard drag, or **Alt + ↑ ↓**, which moves a task one place and past a section's edge into the next section; each is announced. Editors type points in the row (saved on Enter or leaving the field) and add tasks at the backlog's foot. The page reads the board's collection: a move shows at once and is put back if refused.
- **Ranks:** `tl_task.rank` is one fractional order across the project (`sprints/moves.ts` computes a key between the new neighbours); new tasks and imports go last. `rankTasklineTask` saves the sprint and the rank; a sprint change is in the task's history, a reorder isn't.
- **Planning** ("New sprint", anyone who may edit): a name (the next number suggested), the first and last day (the next free days, two weeks; at most 60 days), a goal, with the recent velocity beside it. Up to 10 planned at once. A planned sprint is edited or deleted (its tasks go back to the backlog); an active one keeps its first day.
- **Starting:** one active sprint per project; a sprint planned for later starts today. Its scope then (tasks outside the trash, canceled ones aside; points and count) is its commitment.
- **Completing:** what's done (tasks in a completed status) is stored; the unfinished tasks go to the next planned sprint, a new one starting tomorrow (as long as this one was), or the backlog. A completed sprint doesn't change, and nothing moves into it; its done tasks stay in it.
- **The report** (`$ws/p/$key/sprints/$sprintId`, from a sprint's "Report", Home or the admin): the numbers (committed, done, remaining, days left), the burndown (remaining against the ideal, which falls on working days only) and the burnup (scope and done), the velocity of the last six completed sprints, and the sprint's tasks. `?by=points|tasks`; a switcher opens the project's other sprints. The series come from the daily snapshots plus today's live totals (`sprints/burndown.ts`).
- **Snapshots** (`tl_sprint_snapshot`): the daily job writes each active sprint's close of yesterday, once; starting writes the day before the first day, completing writes today's close.
- **Velocity:** the average completed work of the last three completed sprints (`ProjectTasks.velocity`).
- **Elsewhere:** the task's Sprint and Points fields, a points badge on board cards, the Sprint filter (active, backlog, one sprint) on the board, list and calendar, active sprints on Home and on the admin's overview, and the `sprint` notification (started, completed) to the project's members.
- **Sandbox:** `WEB` plans in sprints: Sprint 1 completed (its days, a velocity of 8), Sprint 2 active (over the velocity, its days so far), Sprint 3 planned, points on most tasks. The demo team's `APP` has the same shape. Sprints belong to their project, so the claim moves them with it.

## Time (0218)

- **Turning it on:** the lead's General settings, "Track time" (on by default): the Time view, a task's Estimate, its timer and its Time tab. Off hides them; nothing logged is lost, and the server doesn't refuse time either way.
- **Estimates** (`tl_task.estimate_minutes`): the task's Estimate field and, for a project estimating in time, the backlog's rows. Durations are typed as people write them (`time/duration.ts`): "1h 30m", "1h30", "2h", "45m", "1:30", "1.5" or "1,5" (a bare number is hours), in Latin or Devanagari digits, with घण्टा/घ and मिनेट/मि. They read back as "1h 30m" ("१ घ ३० मि").
- **The timer:** Start on a task (its header), Stop there or on the topbar's pill (the task, the time so far, Stop), which every page shows while one runs. One runs per person: starting another stops the first and logs it. The server stamps the start, so a reload or another device shows the same time. Stopping logs whole minutes, and drops a timer stopped under a minute; a timer counts 12 hours at most, and the daily job stops one that ran that long and tells its owner (the `timer` notification, digest by default).
- **Time by hand** (the task's Time tab): a day (today or before, after the lock), a duration, a note, billable. The tab shows what was logged against the estimate (over it in the warning colour) and the newest 50 entries; the caller changes or deletes their own, `taskline:time` anyone's in the team. A running timer is stopped, or discarded by deleting it, not edited.
- **My timesheet** (`$ws/timesheet`, the sidebar's "My timesheet" and the palette, `?week=` any day of another week): the caller's week in a workspace from its week start, a row per task they logged on (a project's row for time whose task was purged, read only), days off shaded, totals per row, day and week, the week against their capacity. Each open cell is a field: ↑ ↓ to the row above or below, ← → to the day before or after once the caret is at the edge (a cell's text is selected when it gets focus), Enter moves down (leaving a cell saves it; the last row saves on Enter), Escape puts the value back. Days after today and up to the lock read only. Typing a total changes the fewest entries (`time/sheet.ts`'s `planCell`: a new entry for more, the newest cut for less). "Add a row" offers the caller's open assigned tasks; "Copy last week" fills this week's open days with last week's time on tasks with no time yet this week, and says how many it skipped. An admin without a member row has no timesheet.
- **A project's time** (`$ws/p/$key/time`, a view tab): estimated, logged, billable and estimate left; estimate against actual by task (`?by=task`, a task opens in the sheet) or by member (the estimates assigned to them, logged, billable); the newest entries; time left by purged tasks.
- **The lock date** (`timesheetLockOn`, the admin's "Lock period"): nothing on or before it is logged, changed or deleted, by anyone. It isn't after today; "Unlock everything" clears it.
- **The admin's timesheets** (`/admin/taskline/timesheets`, `taskline:time`): every team entry, newest day first, by member, project, billable and days, with the totals of all that match; edit (the entry form in a dialog) and delete, both audited; the lock; "Export CSV" (all that match, from the server, 10,000 at most). **Utilization** (a tab): each active member's logged and billable time over the days chosen (this week by default, 92 at most) against their capacity there: the weekly capacity spread over the team's working days.
- **Sandbox:** estimates on five of WEB's tasks and a week of time by the owner and the teammates on its working days, with notes in the guest's language, and billable time on the logo. The claim moves the entries; a guest's running timer stops first (one runs per member).

## Timeline, milestones and dependencies (0219)

- **Milestones** (`$ws/p/$key/milestones`, a view tab): a project's checkpoints in their order, each with its day ("Past its date" when it's gone by unfinished), its description, its progress (its tasks done, canceled ones aside, and how many are overdue) and its tasks (open one in the sheet, or all in the list: `?milestone=`). Editors add (a dialog: name, day, description), edit, complete and reopen, move up and down, and delete one (its tasks stay, without a milestone). 50 per project. A task joins one from its Milestone field; the board, list, calendar and timeline filter by it.
- **Dependencies** (the task's Dependencies section, under Work): what blocks it ("Blocked by") and what it blocks ("Blocks"), each with its status and, from another project, that project's name. Editors add one by typing a reference (`APP-4`) or words of a title (the workspace's tasks are searched as the palette's are) and remove one. The tasks may be in two projects of the workspace; the caller must be able to edit both. A task can't block itself, and nothing may close a loop (A blocks B blocks C blocks A): the server walks the dependencies first, under the workspace's lock, so two opposite adds at once can't both pass. 50 on each side.
- **Blocked:** a task is blocked while an open task (not completed, not canceled, not in the trash) blocks it, wherever it is. The board's cards, the list and the timeline show a "Blocked" badge, and every view filters by it (`?blocked=yes|no`). A blocker in a project the caller can't see still blocks: the task's page says "1 more in projects you can't see" without naming it.
- **The completion rule** (the lead's General settings, "A blocked task can't be completed", off by default): moving a blocked task into a completed status (the board, its status field, the list's bulk change) is refused with the blockers' names, and put back. Canceling it still works. Changing a status's category in the workflow settings closes tasks without the rule.
- **The timeline** (`$ws/p/$key/timeline`, a view tab): a row per task with a bar from its start to its due date (either one alone is a one-day bar), over days (`?zoom=day`: six weeks), weeks (`week`, the default: half a year) or months (`month`: a year), from `?date=` (omitted: today), with Earlier, Today and Later. Today's line, the workspace's days off shaded (days and weeks), the milestones as diamonds on their day (in their own row, and on their group's heading when grouped by milestone), and an arrow from each blocker's end to the start of the task it blocks; one whose open blocker ends on or after the day it starts is drawn in the danger colour and its row says "Starts before WEB-2 ends". Rows read earliest first, closed tasks without dates left out; `?group=epic|milestone|assignee` groups them (an epic leads its own group; "No epic", "No milestone", "Unassigned" last). The project's filters apply. A task's title opens it in the sheet; so does a click on its bar.
- **Rescheduling** (editors): drag a bar to move the task, or its end to change its last day; or focus a bar and press **Alt + ← →** (a day earlier or later) or **Alt + Shift + ← →** (the last day). Each change is announced and the focus stays on the bar; it saves through the board's collection (put back if refused). A task without dates has a dashed placeholder on the day shown, where a keyboard step schedules it. A bar outside the range is an arrow at the edge, still movable. Readers' bars don't move.
- **For screen readers** the drawing is hidden and a table says the same: each task's start, due, blockers and warning, and the milestones with their days.
- **Elsewhere:** the activity reads "marked it blocked by WEB-3", "set its milestone to Launch", "completed the milestone Launch"; the admin's activity filter has the new kinds; the admin's JSON export carries the milestones, each task's milestone and the dependencies inside the project.
- **Sandbox:** start dates on most of WEB's tasks, the milestones "Design signed off" (done, with the logo) and "Launch" (in about a week, with five tasks), and four dependencies (the logo blocks the navigation; the navigation and the copy block the launch date; the copy blocks the contrast check, which starts before the copy is due, so the timeline warns). The demo team's WEB has a beta and a launch milestone, start dates and four dependencies. The claim keeps them: they belong to the project and its tasks.

## Custom fields (0220)

- **Two scopes.** The workspace's fields (`/admin/taskline/fields`, `taskline:configure`, audited) are on every team project's tasks; a project's own (`$ws/p/$key/settings/fields`, its lead's) only on its tasks. A task has the workspace's first, then its project's, each in its scope's order. The lead's page lists the workspace's read-only.
- **Types:** text, number, single choice, multiple choice, date, person, checkbox, link. A choice has options (a name and a colour, up to 50, reordered by keyboard in the form). A field's type never changes. 30 fields per scope; a name once per scope, in any case.
- **Values** (`tl_task.fields`, by field id): the task's side panel has an editor per type, saved at once (text, numbers and links when the field is left), each field last-write-wins and in the history ("set Severity to High"). An empty value isn't stored. The server checks every value against its field (`toTaskFieldsSchema`, a person among the workspace's active members); archived and unknown fields are refused.
- **Options by id:** renaming or recolouring one keeps its values; removing one takes it off every task.
- **Archive and delete:** archiving hides a field everywhere and keeps its values (restoring brings them back); deleting removes them (the confirm says how many tasks have one).
- **Required:** a task can't be completed while the field is empty (the board, the task's status, the list's bulk change are refused, naming the fields); creating, importing and canceling aren't. The panel marks it and says what's needed.
- **Filters** (`?cf=<field id>:<value>`, repeated; a select per field in the filter bar, a chip per filter): an option, a person or "Me", ticked or not, before today or from today, a value or empty. The list filters in SQL (`?`, `@>`, the GIN index); the board, calendar and timeline in the browser, the same way.
- **The list** has a column per field, hidden until shown from the Columns menu (`DataTable`'s `defaultHidden`), and in the CSV when shown. The admin's export carries the values as words (a column per field in the CSV, `fields` in the JSON).
- **The CSV import** maps a column per field (guessed by the field's name) and types the cells in the dialog: options and people by name in any case, several options split on `,` `;` `|`, days in the chosen format, yes/✓/हो for a box; a cell that can't be one is a problem in the preview.
- **Sandbox:** WEB's own Area (a choice), Reviewer and Signed off, in the guest's language, with values on most tasks; the claim moves them with WEB and turns the guest's person values into the account's. The demo team has the workspace's Severity and WEB's Reviewer and Signed off.

## Automations and recurring tasks (0221)

- **Two scopes.** The workspace's rules (`/admin/taskline/automations`, `taskline:configure`, audited) run on every team project's tasks; a project's own (`$ws/p/$key/settings/automations`, its lead's) only on its tasks. The lead's page lists the workspace's read-only, and both pages show the run log (the admin's: every team rule's).
- **A rule** is a trigger, conditions and actions (the builder: `automations/automation-dialog.tsx`). Triggers: a task created; its status changed (into a status, a category, or any); its assignee changed; its priority changed (to one, or any); a label added (one, or any); a comment added; all its subtasks done; its sprint started; due within N days, or overdue (the daily job). Conditions, all of which must hold for the task as it is after the change: its type, priority or status category among some, a label it has or lacks, its assignee (someone, nobody, a member), a custom field's value (as the `cf` filters write it). Actions, in order (sortable by keyboard): set the status (one, or a category's first), assign (a member, the lead, the reporter, nobody), set the priority, add or remove a label, move to a sprint (one, the active one, the backlog), make it due in N days, add a comment, notify someone (a member, the assignee, the lead, the reporter, the watchers) with a message, create subtasks. Up to 10 conditions and 10 actions; 50 rules per scope.
- **What a rule may name:** a project rule its statuses, labels (its own and the workspace's), sprints, fields and the workspace's active members; a workspace rule only what every project shares: categories, the workspace's labels and fields, members. The server refuses anything else on save (BAD_REQUEST on the trigger, conditions or actions); what's deleted later makes the run fail, saying so.
- **When it runs:** in the transaction of the change that fires it, after the change's own history and notices: creating a task, a single field changed (assignee, priority, labels added), a move on the board, the task's status, the list's bulk changes, a comment, a sprint started, and from the admin through the app's services. The daily job fires "due soon" and "overdue" once per task and due date (a keyed run, claimed only when the task matches, so a task that matches later still fires; 0226). The CSV import and the tasks a repeat or an automation creates fire nothing.
- **A savepoint per rule:** a refused action (a blocked task, a required field, a quota, a deleted label) rolls back that rule's actions alone; the change stands and the run says why it failed. **No chaining:** what a rule does fires no rule.
- **Whose rights:** a rule's own: a viewer's comment may fire a rule that assigns the task. Its changes read "Automation “Ship it” set the priority to Urgent", its comments are signed with its name, its notices name it ("Automation “Ship it” on WEB-12: Ready to ship"); the "notify" action is the `automation` kind in "My settings" (digest by default). The member whose change fired it isn't told what it then did.
- **The run log:** each time a trigger fired on a task: ran (how many things it changed), skipped (the task didn't match, nothing to change, or past 100 tasks in one change) or failed (why; "assign to the lead" on a project with none fails, it doesn't unassign). A time trigger that doesn't match writes nothing: it looks again every day. Kept 30 days. Each rule shows its last run; a switch turns it on and off at once (the builder's form saves against the rule's `version`).
- **The preview:** "Would match 12 open tasks now", from the conditions as they're typed: the scope's open tasks in active projects, 5,000 read at most ("at least").
- **Recurring tasks** (the task's Repeat field, editors): every N days, weeks (on chosen days), months (on the due day's date; the last day of a shorter month) or years, ending never, on a day, or after a number of tasks. Closing the task (Done, or Canceled to skip one) creates the next one, due on the next occurrence that isn't before today, its start as far ahead: the same title, description, type, priority, assignee, labels, field values, estimate and points, the checklist unticked, in the first open status, outside any sprint. The rule moves to it, so the closed one doesn't repeat again if reopened; trashing the task or "Stop repeating" ends the series. While a task is still open when its next occurrence comes, the daily job creates the next one (the latest occurrence up to today; the missed ones aren't made). The history says "repeated it as WEB-15" and "created it as the next of WEB-12".
- **Sandbox:** WEB's rules in the guest's language: a parent closes when its subtasks are done, new bugs go to Bikash with the Bug label (one run already in the log), a reminder two days before a task is due; the blog post repeats monthly. The claim moves the rules with their project and points the members and merged labels they name at the account's. The demo team has a workspace rule (an urgent bug tells the project's lead), WEB's subtask rule with two runs, and a weekly task in OPS.

## Templates (0224)

- **What one holds** (`template-definition.ts`): statuses (with WIP limits), labels, fields (with options), automations, the project's settings, milestones and sample tasks (type, priority, status, labels, milestone, a parent earlier in the list, start and due as days from the start, a checklist, points, an estimate). Statuses, labels, fields and milestones carry a local uuid the rest refers to; a project gets new ones. A rule may name only those: never a member or a sprint.
- **The built-ins** (`templates/builtin.ts`): Scrum software, Kanban, Marketing campaign, Client project and Event, their words in the creator's language. They read only.
- **Creating from one:** "New project" in the app (the directory's dialog, the template's summary, "Starts on", default today) and the admin (`/admin/taskline/projects/new`). The project gets the template's statuses instead of the workspace's starting ones, and its settings; `project.created` names it. Nobody is notified and no rule fires, as with the CSV import; sample tasks have no assignee, and their creator watches them. A label named like a workspace label uses that one. Quotas are checked first and refuse the whole project. A sandbox has only the built-ins.
- **The team's** (`/admin/taskline/templates`, `taskline:configure`, audited as `taskline.template.*` on the target `taskline-template`; 100 at most, each name once in any case): new, edit (a form with the definition as JSON, checked as it's typed, saved against its `version`), delete (projects made from it keep everything), import (a file read into the same form), export (the file import reads), and "Copy" on a built-in.
- **"Save as template"** (the admin's project page, `taskline:configure`): the project's statuses, its own labels and active fields, its settings, milestones, and rules; its tasks too if asked (200 at most, parents first, without assignees, comments or time). Days count from the project's start, else its earliest date. A rule naming a member, a sprint, or a workspace label or field is left out, and the toast says how many.

## Reports and project updates (0225)

- **A project's reports** (`$ws/p/$key/reports`, a view tab, anyone who can see the project; `?range=4w|12w|26w`, default twelve weeks): by status (every live task) and by priority (open ones); created and completed each week; throughput (completed each week, canceled aside, with the average); overdue at each week's close, by today's due dates; cycle and lead time (typical and 85th percentile, the ten slowest listed); workload by assignee (open, overdue, estimate left, points; nobody's last); time against estimate by person when the project tracks time. Each has "Export CSV" with its own numbers; the cycle report's file has every task in the range, the newest 1,000 at most.
- **Cycle and lead time** (`reports/metrics.ts`): lead from created to completed; cycle from the first move into a `started` status, or from creation if its first move was out of one. Reopening restarts neither; never started means no cycle time.
- **The admin's** (`/admin/taskline/reports`, `taskline:read`): each active project's health, progress (done of those not canceled), overdue, milestones at risk (past their day, or due within a week with tasks open), last activity and the lead's latest update; each active member's open and overdue tasks and estimates against their weekly capacity ("load": estimates due within a week or overdue, over capacity in the warning colour; unestimated tasks count as nothing); and the time logged over `?range=` by project (archived ones too) and by member, as totals. Each table has "Export CSV".
- **Project updates** (the overview's Updates, `tl_project_update`): whoever may run the project posts a health and a rich text post, which sets the project's health and leaves `project.update_posted` in the feed; they can delete one (the health stays). Everyone who sees the project reads the newest 20. An archived project takes none. Nobody is notified. The admin's overview shows when each project's lead last posted; the project's JSON export carries the updates.
- **Sandbox:** Asha's update on WEB in the guest's language, setting its health; the claim makes a guest's own updates the account's. The demo team has two updates on WEB (it's at risk) and a saved template, "Website launch".

## The conversation and notifications (0214)

- **Comments** (the task's Comments tab): rich text with files, by members who may comment (a viewer may; an admin reading or managing through RBAC without a member row may not). Authors edit their own (marked "edited"); the author or the project's lead deletes (soft: `deleted_at`, its files removed). 30 comments per member per ten minutes. Each leaves `comment.added` or `comment.deleted` in the history and moves the `rev`.
- **Mentions:** typing `@` in a comment suggests the workspace's active members (`RichTextField`'s `mentions`; `rich-text-mentions.tsx`). The node is `<span data-type="mention" data-id="…">`, the only `<span>` the sanitizer keeps; the server reads the ids from the sanitized HTML and keeps (in `tl_comment.mentions`) those of members who may see the task. A placeholder can be mentioned; they're never told.
- **Watchers:** creating, being assigned or commenting makes you a watcher; anyone with a member row can watch or stop (the bell in the task's header). Watchers hear about comments and status changes.
- **Files** on a task (its Files section, editors add and remove) and on comments: images and PDFs, uploaded straight to Cloudinary through Taskline's functions (`TASKLINE_UPLOADS`, 60 an hour per member), linked as attachments with `entity_type` `tl_task` or `tl_comment`. Without Cloudinary the task says uploads aren't set up.
- **Notifications** (`notify/produce.ts`, in the change's transaction): assigned, mentioned, a comment or a status change on a watched task, added to a project (from the app's services), due tomorrow and overdue (from the daily job). Never the actor; only members with an account who may see the project; one per person per change. Each kind has a mode: the member's (`/settings`, "My settings", saved on every member row of theirs, with their email language) over the team's (`/admin/taskline/settings`). `off` writes nothing; the others go in the inbox, and `email` on the row says how they're emailed: `instant` (assigned and mentioned by default), `digest`, or `none` (guests).
- **The inbox** (`/inbox`, `?filter=all`, `?page=`): the caller's notifications in every workspace they still belong to, newest first, as sentences from the snapshot in `data` (so they read after a rename); opening one marks it read; read and unread each, or all read. The sidebar's Inbox shows the unread count, polled every minute.
- **Email** (`notify/deliver.ts`, signed Taskline, in the member's email language): after the commit, the service hands the instant ids to `services.deliver` (`waitUntil` in production): one `taskline-notification` email per recipient and task. Within five minutes of an email about the same task, new rows wait for the digest (coalescing). The daily `taskline-digest` lists each person's unread rows not yet emailed. A recipient deactivated, or taken off a private project, since the row was made gets no email about it (the row becomes `none`; 0226).
- **The daily job** (`GET /api/cron/taskline`, `cron.ts`, 07:00 in Kathmandu): stopping timers that ran 12 hours (Task 53; first, so the digests carry its notice), the automations' time triggers and the run log's pruning, repeating tasks caught up (Task 56; before the digests too), due and overdue notices, the digests, sprint snapshots (Task 52), the trash past retention (with subtasks and files), invitations a month past their date. What its steps make with an instant email (someone set `due` to instant) goes out in the same run, before the digests. Each step is idempotent; running it twice changes nothing.

`$ws/p/$key/settings/{general,members,workflow,labels,fields,automations,trash}`, for whoever may run the project (its lead, `taskline:manage`, a sandbox's owner); anyone else who can see it gets the FORBIDDEN page.

- **General:** the project form (versioned) with the done-column days, its state and health, and archiving.
- **Members:** the workspace's active members, added with a role; roles changed; members removed (their history stays).
- **Workflow:** statuses renamed, recoloured, given a category and a WIP limit, reordered with up and down, deleted once their tasks move to another.
- **Labels:** the project's; the workspace's are listed (the admin's, Task 49).
- **Fields** (Task 55): the project's own custom fields (new, edited, reordered, archived, deleted); the workspace's listed.

- **Trash:** restore a task with its subtasks, or delete it for good (`purgeTasklineTask`: its subtasks, labels, watchers, comments, files and history go, a `task.deleted` entry names it, and its number isn't handed out again).

## Workspaces and members (0203, 0207)

- **One team, many sandboxes.** `tl_workspace.kind` is `team` (exactly one, a partial unique index; created by the migration with `{}` settings, so every setting is its default) or `sandbox` (one per user, `owner_id` unique and cascading). A check keeps "team has no owner, a sandbox has one".
- **URLs name a workspace as `$ws`:** the team's slug (`team` by default; the admin's settings change it) or the literal `sandbox`, which always means the caller's own. Nobody can name someone else's sandbox.
- **Members are the identity** everywhere: assignee, reporter, actor, project member, star, watcher. `tl_member.user_id` is nullable: a sandbox's placeholder teammates have none, and deleting an account sets it to null while `display_name` keeps the name history shows. Guests are never team members.
- **Settings are jsonb with defaults in code** (`workspaceSettings`, `projectSettings`): a row stores only what was changed, `.parse()` fills the rest, and a new setting needs no migration. Defaults: projects created by admins only, team visibility, members may join, Sunday–Friday working days, the week from Sunday, Asia/Kathmandu, a 07:00 digest, 30 days of trash, 14 days on the done column, high team quotas.

## Access (0204)

Every app function runs `requireTasklineUser` → `withTasklineServices` (signed in, guests included; `context.user` has `isGuest` and the RBAC `permissions`). Every service then calls **one resolver** before anything else:

- `resolveWorkspace(db, user, ws)` → `{ workspace, settings, member, sandboxOwner, admin, canCreateProject }`
- `resolveProject(db, user, ws, key)` → the above plus `{ project, projectRole, can: { view, comment, edit, manage, logTime } }`
- `assertCan(access, "edit" | "comment" | "manage" | "logTime")`

| Caller | Team-visible project | Private project |
| --- | --- | --- |
| Account not on the team, or a guest | not found | not found |
| Team viewer | view, comment | not found unless a project member (then their project role) |
| Team member | view, comment, edit; may join if the settings allow | not found unless a project member |
| Project lead | everything, project settings included | same |
| `taskline:read` / `taskline:manage` | read only / lead-equivalent | read only / lead-equivalent |
| Deactivated member | not found (history kept) | not found |
| Sandbox owner | lead on everything in their own sandbox | n/a |

- **What the caller can't see is NOT_FOUND** (as the apps, 0187): someone else's data is simply not there. **What they can see but not do is FORBIDDEN**, with a reason the UI shows ("You can see this project but not change it", "This project is archived").
- The highest of the caller's levels wins: their project role, their team role on a team-visible project, and their `taskline:` permission.
- **Archived projects** read only, for everyone, comments included: `assertCan` refuses every action with "This project is archived". A lead (or `taskline:manage`) still has `can.manage`, so the settings open, and `assertCanArchive` lets them restore it (0226).
- **Creating projects:** a sandbox owner always; in the team, `taskline:manage`, or every team `member` when `projectCreation` is `members`.
- **Ids from the browser are checked against the resolved project:** an assignee must be an active member of the workspace, a status and a parent task must be the project's, a label the project's or the workspace's. Anything else is NOT_FOUND.
- **RBAC:** `taskline: [read, manage, configure, time]` in the catalog (inside taskline markers). Any of them opens `/admin` (`canEnterAdmin`); the team role is not an RBAC permission. Admin functions (Task 49 on) follow the CRUD standard: `requirePermission("taskline:…")` → `withServices` → `withAudit`.

## Writes, history and freshness (0205)

Every app write is one transaction: `resolveProject` → the change → `recordActivity(tx, access, …)` → `bumpRev(tx, projectId)` (then notifications from Task 50 and automations from Task 56).

- **`tl_activity` is the app's history,** for members: a task's timeline, a project's feed. App data never goes in the admin audit log (0186); admin-area writes go in both. The actor is the caller's member row; an admin acting through `taskline:manage` without one is recorded with `actor_id` null and `data.via = "admin"`. `data` is short JSON (`ActivityData`): `{ field, from, to }` per changed field of a task, ids and names otherwise. Entries of one change share their time.
- **`rev`** (bigint on the project) goes up with every change to the project or its tasks. Open pages poll it (Task 48) and refetch when it moved.
- **`version`** (an integer on the workspace, the project and the task) goes up only when a form saves: a task's title and description (`updateTask`), the project form (`updateProject`), the settings (Task 49). `saveVersioned` checks and bumps it in the UPDATE's own WHERE; a stale save is a CONFLICT with the `stale` reason, which forms turn into "reload" (`StaleVersionAlert`). Everything else (status, position, assignee, priority, dates, labels, parent, checklist) is a last-write-wins patch that leaves the version alone, so moving a card never makes someone's open description stale.
- `bumpRev` and `nextTaskNumber` set `updated_at` to itself, so Drizzle's `$onUpdate` doesn't move it: bookkeeping isn't an edit.

## Projects, workflow and tasks

- **A project key** is 2–6 of `A-Z0-9`, a letter first (the schema upper-cases what's typed; a check constraint backs it), unique per workspace, and never changes. Task references are `KEY-12`. A deleted project's key is retired (`tl_retired_key`) and refused for every new project (0213).
- **A new project** gets the workspace's starting statuses: the admin's (`defaultStatuses`), or five in the creator's language (Backlog, To do, In progress, Done, Canceled: one per category); its creator as lead (an admin creating one in `/admin` picks the lead, or none) (`lead_id` and a `lead` project member), and a `project.created` entry.
- **Statuses** have a category (`backlog`, `unstarted`, `started`, `completed`, `canceled`), a colour, an order key (`position`, fractional, compared with `COLLATE "C"`) and an optional WIP limit (shown, not enforced). Changing a status's category closes or reopens its tasks. Deleting one moves its tasks, trashed ones too, to the end of `moveTo` (a CONFLICT on the `moveTo` field without it); a project keeps at least one.
- **Task types** offered are the workspace's `taskTypes` (all four by default): the tasks service refuses one turned off (a field error on `type`), a task keeps one it already has, and the panel lists only the offered ones plus the task's own.
- **Labels** belong to a project (its lead's) or to the workspace (the admin's, under Workflows: every project sees them, and a change moves every open project's `rev`); a name is unique per scope in any case (two partial unique indexes on `lower(name)`).
- **Task numbers** come from the project's `task_seq`, incremented by an UPDATE that holds the project's row lock until the transaction ends, so concurrent creates never collide (the unique index on (project, number) is the backstop).
- **`completed_at`** is set when a task enters a `completed` or `canceled` status, kept when it moves between closed ones, and cleared when it reopens.
- **Subtasks** nest three levels at most (`MAX_TASK_DEPTH` 2: epic, story, subtask), in the same project, never under themselves or their own subtasks.
- **The trash:** trashing a task trashes its subtasks that aren't there yet, at the same instant; restoring brings back the ones trashed with it. A subtask restored while its parent is still in the trash comes back as a top-level task. A trashed task can't be changed (CONFLICT) until it's restored. Trashed tasks stay out of lists and quotas; the daily job purges them after the retention.
- **Creating, being assigned and commenting make you a watcher**; watchers hear about comments and status changes.

## The admin (0212, 0213)

`/admin/taskline` is the admin's view of the team (the sidebar group "Taskline"; `taskline:read` opens it, `manage` changes projects, members and invitations, `configure` the workflows and settings).

- **How it writes:** functions in `src/functions/taskline-admin/` (`requirePermission` → `withServices`), services in `src/server/taskline/admin/`, each change audited with `withAudit`. A project change calls the app's own service inside that transaction, as the admin seen as a Taskline caller (`appServices(tx, actor)`: `taskline:manage` is lead-equivalent), so the app's rules, activity and `rev` apply. Activity the admin causes with no member row of theirs is recorded `via: "admin"`.
- **Overview:** active projects, open and overdue tasks, done this week (weeks from the workspace's week start, days in its time zone), created against completed over twelve weeks, each project's health, the people, and the sandboxes as counts only.
- **Projects:** every team project (private ones too) on the list contract; "New project" (key checked while typing, a lead picked or none, the workspace's starting statuses); a page per project with tabs as routes: details (the versioned project form, status and health at once, "Make lead"), members, workflow and labels (shown; edited in Taskline's lead settings, one editor each). Archive and restore, export (JSON: everything; CSV: the tasks), and delete by typing the key, which retires it.
- **Members:** the team with each one's role, title, weekly capacity and open (and overdue) tasks. "Add people" searches accounts not on the team (never guests); deactivating moves their open tasks to another member or leaves them unassigned and ends their access (a 404); reactivating brings them back.
- **Invitations** (their own page, a tab beside Members): by email, with a team role and optionally a project. The `taskline-invite` email, signed Taskline, links to Taskline's sign-up with the project as `?redirect=`. The first session of a verified account with that address joins (Better Auth's `session.create.after` hook calls `acceptOnSignIn`), on the project too, with the invitation's role: a viewer stays a viewer there; expired and revoked ones do nothing; resend restarts the seven days; one open invitation per address. Sending is rate limited per admin (30 an hour).
- **Workflows:** the statuses new projects start with (in order, at least one open and one completed; "built-in" goes back to the five in the creator's language), the task types offered, and the workspace labels.
- **Settings:** the workspace's name and slug (the reserved segments are refused), who creates projects, default visibility, whether members may join, done-column and trash days, working days, week start, time zone, digest hour, the notification defaults per kind (Task 50) and the quotas (never below what exists). Saved against the workspace's `version`. Notifications the admin's changes cause (a member added to a project, a reassignment) are emailed in the digest: the admin's services run inside `withAudit`'s transaction, with no deliverer.
- **Activity:** the team's `tl_activity`, newest first, filtered by project, actor, kind and days, as the app's sentences. The admin's own changes are in the audit log.
- **Timesheets** (Task 53, `taskline:time`): the team's time, its lock date, utilization and CSV ("Time" above).
- **Fields** (Task 55, `taskline:configure`): the workspace's custom fields, with how many tasks have a value ("Custom fields" above).
- **Automations** (Task 56, `taskline:configure`): the workspace's rules and every team rule's run log ("Automations and recurring tasks" above). The project's JSON export carries its own rules and each task's repeat.
- **Templates and reports** (Task 57, `taskline:configure` and `taskline:read`): "Templates" and "Reports and project updates" above.

## Pitfalls already solved

- **The board reads the whole project:** `listTasklineTasks` loads every task of a project outside the trash, for the board, backlog, calendar and timeline alike: about 150 ms and 560 KB at 1,000 tasks, 900 ms and 4.5 MB at 8,000, on PGlite (0227). The list, My work and search stay under 100 ms at that size. A team expecting thousands of tasks in one project needs the board paged by status first.
- **A template's rules:** a rule in a definition is the same shape a project stores, ids included, so they must be the definition's own local ids; `ruleFitsTemplate` is what checks it, on saving a definition and on saving a project as a template.
- **`$onUpdate` on bookkeeping:** an UPDATE through Drizzle moves `updated_at`. `bumpRev` and `nextTaskNumber` set it to itself; use them rather than a plain `update(tlProject)`.
- **Versions aren't `updated_at`:** Taskline's forms compare the integer `version`, not `updated_at` (0122 elsewhere), because last-write-wins patches change `updated_at` constantly.
- **A team reset in tests:** `env.reset()` truncates every table, the migration's team row included. Tests call `ensureTeamWorkspace(db)` in their seed.
- **Activity order within a change:** entries of one transaction share `now()`; order them by kind, not by time, when it matters.
- **The admin through the app's services:** an admin service passes its transaction to an app service (`appServices(tx, actor)`); the app service's own `db.transaction` is then a savepoint, so the audit row and the change commit together.
- **Server field errors use the form's field names:** the settings form's fields are flat (`timeZone`, `projects`), so the service keys its refusals that way, not by the input's path (`settings.timeZone`), or they land in the summary instead of under the field.
- **Unused functions before the pages:** while a module's functions have no page yet, knip can take its file as an entry (`knip.json` and strip-demo's `knipEntries`). Remove the entry once every function is called (Task 48 removed Task 46's).
- **`exists()` around raw SQL:** Drizzle's `exists(sql\`select …\`)` doesn't add the parentheses Postgres needs. Write `sql\`exists (select …)\``.
- **Lanes repeat the statuses:** with swimlanes every lane has a "To do" column, so a column's region is named after its lane too (axe's landmark-unique).
- **A reader's card isn't a sortable:** without a handle, dnd-kit makes the whole card a `role="button"` with links inside (axe's aria-allowed-role); the board attaches the sortable's ref for editors only.
- **Columns are droppables, not sortables:** dnd-kit's optimistic sorting moves an item only over another sortable, so a drop on an empty column arrives as its `target`; `onDragEnd` puts the task at that column's end.
- **A layout's crumb from its loader, under a child that 404s:** the browser hydrates the layout's match without its loader data, so a crumb the server rendered is missing in the browser (React #418). Take such a label from `params` (the `$ws` crumb), as `src/lib/breadcrumbs.ts` explains.
- **A section's accent belongs on `<html>`:** a `data-accent` on the shell's root misses portalled menus and dialogs and the tokens `:root` derives from `--primary`. Use `staticData.brand`.
- **A popup from inside a modal dialog mounts inside it:** Radix makes everything outside an open modal inert, so the mention list, mounted on `<body>` by Tiptap's `props.mount`, couldn't be clicked in the task sheet. `mentionExtension` appends it to the editor's nearest `[role="dialog"]` first, then lets `mount` position it.
- **Admin writes don't email at once:** an app service called from an admin service runs inside `withAudit`'s transaction, which commits after it returns; a deliverer called there would read uncommitted rows. `appServices` passes none, and those notifications go in the digest.
- **A layer's helpers inside another layer's markers:** `todayInZone`, `addDays` and the month helpers sat inside `apps:start`/`apps:end` in `lib/i18n/date-only.ts`, so `strip-demo --keep-taskline` would have removed what Taskline imports; Task 54 found `formatDayMonth` and `formatMonthShort` (`lib/i18n/intl.ts`) the same way. A helper two layers use is core (no markers).
- **A search box that searches as you type jumps too soon:** with exact references redirecting, typing `WEB-1` on the way to `WEB-12` would open WEB-1. The search page's form searches only when submitted; the palette, which only lists, searches as you type.
- **A pointer click on a drag handle starts a drag:** in jsdom, dnd-kit's drag needs `IntersectionObserver`; tests focus a handle (`.focus()`) before pressing Alt + an arrow, as the board's do.
- **The daily job's day is yesterday:** it runs at 07:00 in Kathmandu, so a sprint snapshot it writes is the close of the day before, keyed by that day. A snapshot keyed by the run's own day would show each day's work a day late.
- **A new task's placeholder rank isn't a key:** a task added in the browser sorts last with the rank `~` until the server ranks it; moves skip it when looking for neighbours (`sprints/moves.ts`), or `keyBetweenNeighbours` would throw.
- **Enter in a cell, then its blur, saved twice:** the timesheet saved a cell on Enter and moved the focus, and the cell's blur then saved it again from the render before (the draft was still there), so a typed total went out twice. Enter now only moves the focus (the blur saves); the last row, with nowhere to go, saves on Enter.
- **A helper a loader needs belongs in `search.ts`, not the page:** the utilization route's loader computes the default week; importing it from the page's component module would have put the page in every page's JavaScript (a loader is a route option, 0151). It lives in `admin/search.ts`.
- **A wide table with nothing to focus can't be scrolled by keyboard:** the project's "by member" table and the admin's utilization scroll sideways on a phone but hold no link or field, so axe failed them (scrollable-region-focusable). Their scrolls are `ScrollRegion`s (`components/data-display/scroll-region.tsx`), as the timesheet's.
- **Four tabs don't fit a phone:** the task's Work, Comments, Time and Activity tabs with their counts, and its header's buttons with Start timer, overflowed at 390 px; both wrap.
- **The lock isn't a settings form field:** `setLock` writes `timesheetLockOn` without the workspace's `version`, and the settings form keeps what it doesn't edit (`{ ...stored, ...form }`), so neither undoes the other.
- **A Gantt bar is a button, not an SVG shape:** focus rings and accessible names on SVG elements aren't reliable across browsers, so the timeline draws its grid and arrows as one hidden SVG and positions the bars as `<button>`s over it; their `aria-label` holds the visible title (axe's label-in-name).
- **A drag that ends on a bar is also a click:** the pointer's `click` follows `pointerup`, so a bar dragged to a new day would open the task too. The timeline marks a moved drag and skips the click that follows it.
- **Several selects of one name are one list param:** the filter bar has a select per custom field, all named `cf`; `formSearchPatch` used to make a list only of checkboxes, so the first select's value won. It now makes one of any name several controls share, and `FilterBar` shows each select the list's entry among its options.
- **A column hidden by default needs its own memory:** the table preference remembered hidden columns only, so a field column that starts hidden couldn't be remembered as shown. `shownColumns` holds those, written only for `defaultHidden` columns, so other tables' cookies stay as they were.
- **One connection per transaction:** inside a transaction, `Promise.all` sends several queries down one connection at once (pg warns: "client.query() when the client is already executing a query"). Read one after another in code that runs inside a write (Task 56's rule checks and the admin's automations view do); `taskDetail`'s reads inside a write still do it, a known warning.
- **A rule's comment beat its notice:** one person hears once per change, and a rule that comments and notifies made its comment's notice first, so the "notify" was lost. The engine puts a rule's own `automation` notices first.
- **`tsc` at Node's default heap:** with about 150 routes, `tsc` needs about 2 GB, Node's default heap on a 12 GB machine; Task 56's two routes tipped it into "heap out of memory". `pnpm typecheck` passes `--max-old-space-size=4096` (0222); run it, not a bare `tsc`.
- **Route definitions are in every page's JavaScript** (0151): Taskline's eleven routes of Task 47 cost 3.2 kB gzip of entry, the thirteen of Task 48 2.7 kB. Keep heads, guards and loaders small; components, queries and DB are split out. A shift in Rolldown's chunks can also move the count (0211: clsx has a code-splitting group of its own).
