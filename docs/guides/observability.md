# Observability: logs, Sentry, PostHog and feature flags

All optional except the logs. Without their variables, Sentry and PostHog are off: nothing is initialised or downloaded, no consent banner, no network calls. Example: `/dev/examples/analytics`.

## Logs

- **One request id per request** (`src/server/http/request-scope.ts`, 0123): generated by the server entry (and by `defineApiRoute` for a route), returned as the `x-request-id` header, and attached to every log line, every server Sentry event and the `AppError` the user sees (the error page shows it as "Reference"). A support report or a response header leads to the log lines and the Sentry event.
- **`log(level, msg, fields)`** (`src/server/log.ts`) is the server's one writer: a JSON line whose first fields are always `time`, `level`, `msg`, `requestId` and `userId` (both from the request's scope, once known), then the event's own. Don't call `console.*` in server code (Biome's `noConsole`).
- **Redacted on the way out (0300):** a field named like a secret (`password`, `token`, `secret`, `authorization`, `cookie`, `apiKey`, `signature`, `otp`, `backupCodes`…) is written as `[redacted]` at any depth, and every string loses what looks like one: a URL's `user:password@`, `Bearer …`, a JWT, `token=`/`password=`/`code_verifier=` in a query, and all but the first letter and the domain of an email address (`a***@example.com`). Long strings, long lists and deep objects are cut. So a caller can log an object it was given without first checking it.
- **Errors in a line:** `errorFields(error)` gives its message, its own name and its cause chain (`causes`, each with its code: Drizzle's wrapper and the driver's SQLSTATE). `errorFields(error, { stack: true })` adds the stack, for a failure nobody expected; an expected one is logged without it.
- **The lines a request leaves:** `server-fn` per server-function call (name, method, duration, outcome), `api-route` per server route (route, method, status, duration), `outbound` per call to another service (service, method, path, status, duration, attempts; never a header or a query string), `cron` per job and `cron step failed` per failing step, and `slow request` past `SLOW_REQUEST_MS` with the parts `Server-Timing` names.
- **Levels:** expected refusals (4xx `AppError`) log as `warn`, failures as `error`. A database, Zod or service error that was mapped to a code is one `mapped error` line at `warn`, with its causes; a bug is one `unexpected error` line at `error`, with its stack (`toEnvelope`, `src/server/http/errors.ts`).
- **What nothing caught** (an unhandled rejection, an uncaught exception, an error that escaped a request) is one `unhandled error` line with its stack and Nitro's tags, and a Sentry event (`src/server/plugins/process-errors.ts`, Nitro's `error` hook).
- **The browser's errors** reach the server log when Sentry is off (0300): an uncaught error, an unhandled rejection or what an error boundary caught is posted to `POST /api/client-errors` (`src/lib/observability/client-errors.ts`, loaded on the first error), once per message and five per page at most. The server checks its shape, caps its lengths, strips the page's query and hash, allows 10 a minute per client, and writes one `client error` line with the request's id and, for a failed server call, its `failedRequestId`. With a DSN the errors go to Sentry instead.

## Sentry (`VITE_SENTRY_DSN`)

- **Browser** (`src/lib/observability/sentry-client.ts`) and **server** (`src/instrument.server.ts`, imported first by `src/server.ts`): errors and performance traces, including router navigations.
- **The browser SDK loads after the entry chunk** (0152): `src/client.tsx` starts loading it in parallel with hydration, and errors before it's ready are buffered and sent once it is. In code that also runs in the browser, call `captureException` / `setSentryUser` from `sentry-client.ts`, never import `@sentry/tanstackstart-react` statically (one static import puts the whole SDK back in every page's JavaScript; the bundle budget catches it). Server-only code imports it inside `.server()` or a server module.
- **Traces:** 10% in production. None in development unless `VITE_SENTRY_DEV_TRACING=true` (tracing every dev request slows `pnpm dev`).
- **What's reported:** unexpected server-function and server-route errors, once, with the original stack; a job's failing step (tagged `cron` and `step`); what nothing caught (`process-errors.ts`). Every server event is tagged `requestId` (`beforeSend` in `src/instrument.server.ts`). Expected `AppError`s (below 500) aren't reported, and the browser doesn't log them either (`onCaughtError` in `src/client.tsx`).
- **Privacy:** only the user id is attached; the IP address is stripped.
- **Source maps** upload during `pnpm build` when `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` are all set.
- **CSP:** the ingest host is added to `connect-src` only when a DSN is configured.
- **CSP violations** reported by browsers arrive as warnings titled `CSP violation: <directive> blocked <resource>`, one issue per directive and resource, with the page path in the extras (0139). The log line is `csp violation`.

## PostHog (`VITE_POSTHOG_KEY`, optional `VITE_POSTHOG_HOST`)

- **Opt-in:** a consent banner stores the choice in a cookie (`analyticsConsent` preference), rendered on the server so nothing shifts. The footer link changes it later.
- **Before consent:** `posthog-js` isn't downloaded, `track()` is a no-op, and the server sends no events.
- **After consent:** pageviews on navigation, `identify` on login and `reset` on logout, plus feature events: `test_crud_created`, `test_crud_updated` and `test_crud_deleted` (server) and `test_crud_viewed` (browser).
- **In features:** call `track("event", props)` freely; it does nothing without consent.
- **Web Vitals (0138):** after consent, `src/lib/observability/web-vitals.ts` sends a `web_vital` event per CLS, LCP and INP measurement (`metric`, `value`, `rating`, `navigation_type`, `path`). Watch the production CLS rule with a trend insight on `web_vital` filtered to `metric = CLS`, aggregated as the 75th percentile of `value`, broken down by `path`: it should stay at or below 0.01 (and LCP under 2,500 ms, INP under 200 ms). Values cover a whole document visit, client-side navigations included.

## Vercel Web Analytics (0253)

- **Where:** `<Analytics />` from `@vercel/analytics/react` in the root layout (`src/routes/__root.tsx`), so every page counts, client-side navigations included. Not `@vercel/analytics/next`: this app isn't Next.js.
- **Vercel builds only:** `vite.config.ts` defines `import.meta.env.VITE_VERCEL_ANALYTICS` as `"true"` when `VERCEL` is set at build time. Dev, local builds and e2e render nothing, because `/_vercel/insights/script.js` exists only on Vercel and its 404 would fail the browser review's console check.
- **Turn it on** in the Vercel project (Analytics tab); until then the deployed script 404s and logs one line.
- **No consent needed:** it sets no cookies and stores no personal data, unlike PostHog above. The CSP allows it as is: the script is same-origin and injected by the nonce'd bundle (`'strict-dynamic'`), and it reports to `/_vercel/insights/*` (`connect-src 'self'`).

## Feature flags

- **Evaluated on the server** in a loader (`src/functions/feature-flags.ts`) and SSR'd through the Query cache, so the server and browser render the same thing and the browser makes no flag request.
- **Never slow (0154):** with `POSTHOG_SECRET_KEY` (a Project Secret or Personal API key) flags are evaluated in memory from definitions polled every 30 s. Without it a flag request gives up after 300 ms (the flag is off) and answers are cached for 30 s per flag and visitor.
- **Unknown or unconfigured flags are off.** Before consent, flags are evaluated with a shared anonymous id and never record `$feature_flag_called`.
- **Example:** create a boolean flag `home-items-cta` in PostHog to show a call to action on the demo home (`/dev`).

## Health

- **`GET /api/health`** (and `HEAD`) is for uptime monitors (0124): `200` with `{ status, checks: { database: { status, latencyMs } }, checkedAt }`, or `503` when the database doesn't answer within 3 s. Never cached, no failure details (they're in the log line).
- **`/health`** shows the same check as a page for people (noindex).

## Pitfalls already solved

- **Expected errors aren't logged:** `src/client.tsx`'s `onCaughtError` skips AppErrors below 500 (a 403 page is the intended result). Don't add `console.error` for them elsewhere.
- **A log line is redacted, not trusted to be clean:** don't add a field because "it's only an id" and name it `…Token`; a name that ends like a secret is dropped whatever it holds (`tokenCount` is fine, `refreshToken` isn't).
- **`Server-Timing` is public:** its parts are names and durations only. Don't put a user's data in `recordTiming`'s description.
